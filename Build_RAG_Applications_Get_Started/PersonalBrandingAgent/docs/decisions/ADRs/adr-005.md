# ADR-005 — Operational Memory Kept Separate from the RAG Chroma Collection

## Status

Accepted (see `../phases/phase-10-observability-memory.md`).

## Context

The system needs two memories: what is known about the user, and what the
system has done. Mixing them lets a generated post become "evidence" for
the next post — the loop the corpus's own audit policy exists to prevent —
and makes run history queryable only by semantic search instead of by exact
query.

## Decision

Knowledge lives in `data/` → Chroma; operational state (runs, phases,
checkpoints, lifecycles, intents, publications, failures, notifications,
locks, credential expiry) lives in application-owned SQLite, with
correctness in constraints rather than callers. Publishing history is
answered by deterministic SQLite queries exposed as a read service, never
by retrieval.

## Consequences

- "What did this run do / what went out / what failed" are exact queries,
  independent of log retention.
- Local publication history is authoritative (LinkedIn grants no read-back)
  and therefore not rebuildable — unlike `chroma_db/`.
- Cost: a derived Chroma view of history is deferred until evaluation
  demonstrates a real benefit, and may never come.
