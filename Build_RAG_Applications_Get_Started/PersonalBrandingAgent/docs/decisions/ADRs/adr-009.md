# ADR-009 — Stale Locks Recover on Liveness, Never on Timeout Alone

## Status

Accepted (Step 12; see `app/workflows/scheduled.py`, Known Issue #16).

## Context

Step 1's lock reclaims on expiry alone. That is a correct primitive but a
dangerous policy for this workload: an 8-hour workflow that overruns its
TTL is still a live owner, and handing its lock to a second invocation on
timeout alone would silently twin two live processes over irreversible side
effects.

## Decision

Owners are `hostname:pid:token`. An expired lock whose pid is demonstrably
alive on this host is refused, never reclaimed; only a demonstrably dead
owner is taken, through the atomic Step 1 transaction (so two simultaneous
recoveries cannot both win). Doubt fails closed: unparseable owners and
ambiguous liveness both refuse — a missed run, never an overlap. Every
recovery is recorded; TTL (6h) sits below the shortest schedule interval
(8h) so a crashed holder is always reclaim-eligible by the next tick.

## Consequences

- Overlap is impossible by construction, including across TTL overruns.
- Accepted residual: pid reuse can make a dead owner's lock look live
  (repeated refusals until the pid dies; operator-clearable). Documented,
  not fixed — the safe direction.
