# ADR-006 — Freshness Is Read from `sync_checkpoints`, Never Re-derived

## Status

Accepted (see `../architecture/data-flow.md` §3, `../architecture/system-overview.md` §4).

## Context

"How current is this evidence" could be answered by re-inspecting sources at
read time — expensive, racy, and a second definition of synchronized — or by
trusting the record the synchronization already wrote.

## Decision

Freshness comes from the `sync_checkpoints` table (last successfully
processed revision + timestamp per source), which advances only after a
fully successful sync. The context layer reads it; nothing recomputes it;
a store that cannot be read fails the run rather than degrading to an
"unknown freshness" the generator could misread as current.

## Consequences

- One writer (sync), many readers, no drift between "synced" and "fresh".
- Cost: freshness is only as honest as the checkpoint discipline — which is
  why the checkpoint moves exclusively on success.
