# ADR-008 — Cron (Not a Systemd Timer, Not a Python Scheduler) Triggers the Workflows

## Status

Accepted (Step 12; closes `PLAN.md` §12.2 open item D; see `ops/personal-branding-agent.cron`, `docs/operations/scheduling.md`).

## Context

Two periodic jobs (branding every 8h, sync every 24h) on one user's machine
needed a trigger. Candidates: a long-running Python scheduler, a systemd
timer, or cron. A Python scheduler would add a process, dependencies, and
failure modes for two fixed intervals; the choice was between the two
OS-level triggers.

## Decision

Cron. One file, no daemon-reload, no lingering, no dependency on a running
systemd init — sufficient for fixed coarse intervals with no dependencies
between units. Each line runs the Step 11 entry point once and exits with
its status (`0` success · `1` failed · `2` needs a person · `3` locked
out), unmasked. Overlap protection, stale recovery, and exit semantics live
in the application (`app/workflows/scheduled.py`), not in the trigger.

## Consequences

- Nothing long-lived to monitor; scheduling adds zero runtime code.
- Revisit for systemd timers if sub-minute granularity, unit dependencies,
  or journal integration become requirements.
